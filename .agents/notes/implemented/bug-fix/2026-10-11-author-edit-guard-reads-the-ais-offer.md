# Agent Note: 作者答应 AI 对手改文件的提议时放行；「你说改我就改」也算提问

Status: implemented

相关：`bug-fix/2026-10-09-agent-respects-author-manual-edits.md`（作者手改保护本身）。那份 note 的「上一轮问过的文件，作者回『好 / 可以』就放开」被否，理由是 AI 默认问的是「要把第2章也改成老秦吗？」。本 note 部分推翻这个结论：守卫现在读上一轮 AI 的提议原文，按 AI 实际问的是哪个文件来判断「好」答应的是什么。其他规则不变。

## Problem

10-10 至 10-11 线上 2 个会话、2 位作者（I14），都在 #163 守卫上线之后：

- AI 自己提议「按这个改（…），我直接写进第四节」，作者回「好的，继续」，`edit_file` 被拒，AI 让作者照抄「第四节按…改」。作者下一条放弃：「第四节先不动」。
- AI 给出「1. 大纲那三处按新来历改掉 2. 先把第二章重复的那段压掉 3. 两件都做」，作者回「两件都做」，大纲被拒，AI 又让作者说「大纲按新来历改」，会话就此结束。前一轮作者回「按新来历修改…」（复述选项 1），也被拒了。

逐条重放后，所有原话在 `request_targets_file` 里都是 False，只有 AI 口述的口令是 True。原因是守卫只看作者这一轮的关键词。`author_confirms_change` 只认「统一成老周」这类带方向的改名，所以「好」「两件都做」「1」永远不放开。旧 note 默认 AI 问的是别的章，但线上 AI 问的就是这个被保护的文件，作者只能学口令。

I06 里还有一个同类情况。AI 结尾写「要不要我把核心大纲那一行同步改成这个新落点？你说改我就改，不改就留着。」，作者回「改」。`_should_clarify_first` 要求上一轮以问号收尾，而这句以句号结束，于是作者被当成提了笼统要求，又被追问一次。

## Decision

**守卫读上一轮 AI 的提议（`agent/tools/author_edit_guard.py`）**

- `previous_offer_items(reply)`：从上一条 assistant 回复的结尾读出提议，回复取自 `previous_offer_from_history`，去掉 session_loader 追加的合成段落。提议包括：末尾那一串选项（`1.` / `-` / `A.`，按出现顺序编号；「两件都做 / 都改」标成 `picks_all`），选项前两行里的问句，没有选项时最后三行里的问句。问句包括「你说一声我就动」「需要你点头我才改」这类不带问号的提问。问句从发问的那一分句算起；那一分句没点名文件时，再带上前一分句。前面交代做了什么的句子（「第3章改好了」「我没动它」）不算提议。
- 一项提议「要改这个文件」的条件：有改动的说法（`_EDIT_VERBS` 再加「写进 / 补 / 压掉 / 理顺 / 换」等），并且点名了这个文件（标题、标题里的词、第 N 章 / 节、大纲这类类别）。点名必须在不带「先不动 / 留着 / 保持原样」的分句里；第一分句就是「先不动」的选项整项不算。「第九章细纲」是大纲里的一段，不算点名第九章正文。AI 发问时的「要不要 / 需不需要」不按否定处理。
- 作者怎么回答算数（`author_accepts_offer`），带「不用 / 先不 / 保持 / 算了」等不改说法的一律不算：
  - 选第几项（「1」「选第一个」「方案二」）、「两件都做 / 都改」、或者复述了某一项的说法。复述指至少 4 个字连续相同、只出现在这一项里，并且复述所在的分句没点名别的文件；「第5章的开头改紧凑一点」不算选了「把第3章开头改紧凑一点」。选中的项里有一项要改这个文件，就放行。
  - 只答应（「好的，继续」「可以」「改」「按这个改」，去掉这些词后什么都不剩）：按第一项提议算（问句在前、选项在后，没点名任何文件的项跳过）。第一项要改这个文件才放行。第一项是「先不动」、或第一项改的是别的文件（「要把第2章也改成老秦吗？」），这个文件都不放开。答应之外还提了别的事（「好，继续写第五节」）不算只答应。
  - 上一轮 AI 没提议改它（只交代做了什么、问的是别的章、没有提议）时，「好」照旧不放开。
- 不改落库格式。提议原文本来就在历史消息里，`service.py` 每轮用 `previous_offer_from_history(history_messages)` 读出来，经 `ToolContext.set_context(author_previous_offer=…)` 放进 `AuthorScope.previous_offer`，`request_targets_file` 在 `confirmed_file_ids` 判断之后检查它。已经落库的线上会话不用迁移，下一轮就生效。
- 删除（`delete_file`、递归删除）不走这条，仍要作者点名并说删。
- 拒绝说明（`protected_refusal_message`）不再要求作者「自己说清把这个文件改成哪种写法」才改。作者要的修改正落在这个文件里时，说明让 AI 讲清打算怎么改，并给一个点名这个文件的选项（「按这个改，写进第3章」），作者回「好」或选这一项就能改，不要让作者照抄口令。「不要提议把作者改的写法改回去」和「默认建议改其他章」保持不变。

**笼统要求先问清楚（`agent/graph/writing_graph._should_clarify_first`）**

上一轮最后一句是「你说改我就改」「你说一声我就动」这类提问（`ends_with_conditional_offer`），并且收尾的提问里只提了一处修改（`previous_question_offers_one_edit`，未改）时，作者的「改」就是答应这一处，不再先问。「回复协议每轮都给选项」的规则不变：只有选项、没有提问时照样先问。

## Alternatives considered

- **工具卡片上加「允许 AI 改《X》」按钮，带结构化的 `confirm_edit_file_ids`（评审建议 1）。** 最强理由：确认完全不靠文字理解，最准。没采用（这一批）：要改前端卡片、SSE / 请求协议和 i18n，Vercel 和 Railway 上线有时间差，会出现 422（见部署错位记录）；作者回文字的路径无论如何都得能用，因为线上作者就是这么回答的。以后可以加上这个按钮，与本 note 并存。
- **保存时把 AI 问的是哪个文件解析出来写进 routing（评审建议 2 的原方案）。** 最强理由：判断只做一次，下一轮不用再解析。没采用：保存时只知道被拒的文件 id，不知道 AI 回复里点名的标题对应哪个文件，要另外查库。下一轮守卫手里正好有这个文件的标题、类别和章号，直接拿提议原文比对更准；也不改落库格式，线上已有的会话下一轮就生效。
- **「好 / 可以」一律放开上一轮被拒的文件。** 最强理由：最简单，线上两例都能修好。没采用：旧 note 第三轮评审的场景依然成立。AI 问「要把第2章也改成老秦吗？」时，「可以」答应的是第2章，把被拒的第3章放开，AI 就会在统一人名时把作者的改名改回去。现在按 AI 实际提议的是哪个文件判断，这个场景照样拒（有回归用例）。
- **补关键词：把「重新生成 / 按建议改」加进改动说法，放宽「正开着的文件」那条里对别的章的排除（评审建议 3）。** 最强理由：能顺带覆盖 U079 第一次被拒（作者贴了审稿建议，里面带「后面第六节要靠它」）。没采用：这两条是旧 note 几轮评审收紧过的，放宽会重新放开「写第六节，这里节奏改快点」这类场景；而且那两次被拒的第四节、第五节都是 AI 前一轮刚写的，更可能是「作者手改」判错了（见 Consequences），不该靠放宽关键词掩盖。

## Consequences

- 收益：AI 提议改作者手改过的文件，作者回「好的，继续」「1」「两件都做」或复述那一项（「按新来历修改」）时，这一轮就能改，不用再学口令。AI 问的是别的章、只交代做了什么、作者说了不改时，照旧不放开。AI 结尾写「你说改我就改」、作者回「改」时不再被追问。
- 代价：
  - 提议和回答都按文字规则判断。AI 不点名文件、只说「那三条」时（U079 17:00，「使用三条可选建议，重新生成」），守卫认不出提议改的是哪个文件，仍会拒一次。复述匹配用的是「4 个字连续相同」，作者凑巧复述了某一项、而那一项正好改这个文件时会多放开一次；复述所在分句点名了别的文件时不算，这能挡住大部分误放。
  - 「好」按第一项算。AI 把改作者手改文件的提议放在第一项、作者其实想选别的，又只回了「好」时，会放开这个文件。提示词没有规定推荐项放在哪里，但 `PLANNED_WRITER_AFTER_QUESTION_NOTE` 里「没有推荐就按第一个」也是这个口径，线上 AI 也按第一项理解作者的「好」（U079 16:40 的路由理由是「确认按第一方案改第四节」）。
  - 选中的一项同时点名了几个文件（「大纲那三处…第五卷…」）时，这几个文件都放开。「第N章细纲」除外。
  - AI 如果违反提示词、直接提议「把第3章改回老周」，作者回「好」，就会改回去。这是作者答应了一个点名的问题，算作者的决定。
  - 每次检查被保护的文件，要对作者回复的前 300 字和每项提议（最多 12 项、每项 240 字）做一次最长公共片段比对，开销很小。
  - 没解决的部分：U079 里第四节、第五节都是 AI 前一轮刚写的，几分钟后就被判成「作者手改」。可能是编辑器自动保存、或系统备份留下了非 AI 版本，要查这两个文件的 file_versions 才能确认（这一批没有线上数据权限）。回复里先说「重写好了」、后说「我没动它」，是 writer 提示词里的进度句和流式输出造成的，不在这一批。

## Verification

`cd apps/server && .venv312/bin/python -m pytest tests/test_agent/test_author_edit_guard.py tests/test_agent/test_author_scope_graph.py -q --no-cov`：`TestReplyToThePreviousOffer` 用构造文本覆盖以下情况：

- 工具层：`edit_file` 在作者回「好的，继续」时改成功；作者再次手改后，AI 问的是别的节、作者回「好」时仍被拒。
- `_should_clarify_first`：以「你说改我就改」结尾、作者回「改」时不再先问。

改动前，前两组断言因为没有 `previous_offer` 都会失败；用本地脚本把 U079 / U094 / U066 的原文逐条重放，改动前全是 False，改动后答应的那几条是 True，别的文件仍是 False。旧 note 里「好 / 可以 / OK」在没有提议时不放开第3章的用例原样通过。
