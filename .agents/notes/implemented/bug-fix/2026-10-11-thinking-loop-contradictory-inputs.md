## Problem

r5（prod-v2026.10.10.3，10-10 02:57 上线）之后仍有 4 处退化思考（I07 证据）。对话记录里思考只保留开头和结尾，中间部分没有；下面的「证据」都来自开头/结尾片段、工具调用序列、交接内容和路由，结合代码还原模型当时收到的系统提示和交接消息。

### 案例 1：1010-U070，10-10 07:23:49，writer 思考 204,266 字，「OK」×5629，output_truncated

- 作者原话只是补人设：「预计800章左右，主角姓名陈屿，年龄22大学刚毕业……」。路由 planner → ['writer']、scope 为空、`write_content=true`（路由按「补答上一轮」沿用了上一轮的 true，上一轮其实已经交付并以选项收尾）。
- planner 更新了总纲和细纲，以选项收尾、没有显式交接；计划序列照样把 writer 拉起来。
- writer 收到的指令同时有三条：
  1. 系统提示末尾「本轮用户范围约束 [最高优先级]」：「作者本轮已经要求写正文：规划 / 设计完成后直接交接 writer 写正文，结尾不要问作者要不要开始写。」——这是 `_build_scope_directive` 为规划类角色加的一句，但 `state["scope_directive"]` 是整轮共用的，writer、审稿人也会收到；
  2. 计划交接说明：「作者要的已经全部交付时，用一句话确认后直接结束」；
  3. WRITER_PROMPT：「上一位已经把作者要的内容写完时，简短确认后结束」。
- **证据（直接）**：writer 思考开头逐字引用了第 1 条，并立刻指出它和作者原话矛盾：「但用户本轮范围约束说「作者本轮已经要求写正文…」……嗯，但作者本轮消息只是给设定，没有明确要…」。「作者要正文」被写成最高优先级的事实，「已经全部交付就结束」就无法成立；而又没有任何可写的正文范围。之后就是 OK/Hmm/Output 短句循环直到 64000 上限。
- 判断：触发条件是写给规划师的那句约束出现在 writer 的系统提示里（把一个错误的事实以最高优先级告诉 writer）。路由把 `write_content` 判成 true、计划交接在规划师已交付时仍拉起 writer，是让这句话出现的前提，但不在本包范围（见 Consequences）。

### 案例 2：1010-U074，10-10 05:38:44，审稿人思考 209,395 字，结尾满屏「.」，output_truncated

- 作者：「帮我写完小说，并生成大纲……然后对这个小说进行剧本创作」。路由 planner → ['writer']，scope「先出大纲，再补全小说并做剧本创作」，`write_content=true`。正文是一个 14.3 万字符的单文件（第 1—100 章）。
- planner 写了两份大纲，交给 writer「可分批写（建议每批 3—5 章）」；writer 用 edit_file 追加第 101—105 章，按 WRITER_PROMPT 送审；审稿人这一次运行**没有调用任何工具**，一个思考块 209k 字后撞上限。
- 还原出审稿人收到的输入里有四处冲突：
  1. 同案例 1，系统提示里有「规划完成后直接交接 writer 写正文」，而 QUALITY_REVIEWER_PROMPT 只允许为客观缺陷交接、不需返工时它的回复就是最终回复；
  2. `[待审查内容]` 取的是整份文件（`_collect_review_payload_text`）再按 9000 字符截头尾（`_format_review_payload` 70% / 30%）：头部 6300 字符是**第 1—4 章旧稿**，尾部 2700 字符只覆盖新写的五章（约 3000 字）的后半，中间标「[中间省略 10 万字]」。HANDOFF_READ_RULE 又要求「待审查内容中已给出的正文直接使用，只读缺失或截断的部分，不重新通读全部资料」——缺的正好是要审的内容，而读它只能把 14.8 万字符整份读回来；
  3. 「[质量检查任务] 不需要返工时…第一行说本轮写好了什么（文件名、`word_count` 字数）」，而字数只能来自工具结果：writer 的 edit_file 结果不跨 agent 回放，交接里只有「约3089字」（禁止写「约」），query_files summary 在截断时不带 `word_count`，唯一来源又是整份全文读取；
  4. scope 要求补全到第 122 章并做剧本，writer 只写了第一批就送审；审稿人不能写、按提示也不能为「继续写」交接。
- **证据**：思考开头「The 待审查内容 shows the beginning of the file (chapters 1-4) and then the newly written chapters 101-105 (with the middle omitted). There's an au…」，说明它注意到了第 2 处。作者回「继续」后（同样被路由回审稿人），审稿人先搜、再把全文读完，交接 writer 续写——即在 05:38 那次运行里它面对的就是「要不要整份重读 / 能不能交接续写」这类选择。思考中段丢失，**无法确认四处里哪一处是触发点**。

### 案例 3：1011-U094，10-11 08:49:11，审稿人一个思考块 35,444 字，「Hmm」×1218，本轮输出 155,544 tokens（end_turn）

- 作者要「按现有素材改设定后写第3-10章」。writer 新建 8 个章节文件（合计约 2 万字），送审；审稿人读了 9 个文件，在思考里逐章手算「理智」数值链，然后交回 writer 返修 4 处。
- 155k tokens 里相当一部分是正常产出（8 章正文 + 审稿 + 返修，I07 verdict 已指出）。退化的那一块出现在逐章核算数值链时（片段：「Now let me verify the full chain. ch3 (day 3): 61 → -1 (伤口) 60 → …」），结尾「Hmm, hmm. Hmm. Hmm… Let me go.」后正常交接。
- 在这一块之前审稿人还反复权衡要不要读第 4、5、6、8、9 章（「do I even need ch5/ch6?…read ch4 and ch8… Ugh. OK let me just do ch4, ch8, ch9」）：8 个文件拼起来远超 9000 字符预算，`[待审查内容]` 只剩头尾，中间几章只标「[中间省略 N 字]」，看不出缺的是哪几章。
- 同一会话 07:16 的审稿人和 08:49 的 writer 都出现过「The summary (mode) didn't return word_count. Hmm. … I need word_count」。全部对话里有 11 个会话的思考片段出现同样的话（U044、U068、U070、U072、U076、U083×2、U086、U088、U091、U094），其中 1010-U072 审稿人一个 19,628 字的思考块就是以这句开头的。
- 判断：**没有找到让数值核算本身陷入循环的矛盾指令**。这一块更像长时间手算后的退化；本轮只去掉了它前后的两处多余权衡（字数、缺哪几章），不宣称修好。

### 案例 4：1011-U094，10-11 09:09:28，审稿人思考 78,068 字，「Hmm」×203（end_turn）

- 作者回答上一轮的选项 1：「按新来历修改，修改之后再按新的重写1-10章与新设定冲突的内容」。writer 改了三个正文文件；改大纲被「作者手改保护」拒绝（`author_edit_protected`，作者原话没有点名大纲）。writer 的交接里没提这件事。
- 审稿人看不到这次拒绝（工具结果不跨 agent 回放），把「大纲里那三处旧口径这轮没改」列为必改项交回 writer；writer 只能再说明一次改不了——一个工具层在本请求里不会放行的要求。
- 判断：这是一个确凿的「要求做但做不到」的输入，但它出现在审稿人退化之后的交接里，**没有证据表明它就是那 78k 字思考的触发点**；思考中段同样丢失。

## Decision

**1. 规划类专用约束只给规划类角色（`agent/graph/writing_graph.py`）**

- `_build_scope_directive(routing_metadata, *, agent_type=None)`：「作者本轮已经要求写正文：规划 / 设计完成后直接交接 writer…」只在路由初始 agent 是 planner / hook_designer **且**这次要跑的 agent 也是规划类角色时加入。read_only、`write_content=false` 的约束和「用户要求的交付范围：…」仍给每个 agent。
- 图在每次跑 agent 前按当前 agent 重新生成 `scope_directive`（为空时移除），`nodes.run_streaming_agent` 的拼接方式不变。P2-21（规划师以提问收尾时保留 writer）的行为不变：planner 仍收到这句，writer 仍从计划交接说明里拿到 `PLANNED_WRITER_AFTER_QUESTION_NOTE`。

**2. 送审内容只附本请求改动的那一段（`writing_graph._collect_review_payload_text` / `_review_payload_block`）**

- `ToolContext` 新增请求级的 `_PreWriteContents`：AI 第一次覆盖某个文件的正文之前记下原正文（`file_ops/edit.stage_pre_ai_write_backup` 是 update_file 与 edit_file 共同的必经点，在那里调用 `remember_pre_write_content`；create_file 新建的文件记为空串）。只记第一次，后面的写入覆盖的是本请求自己的字。没有请求上下文（非应用内对话）时什么也不做；记录失败只记 DEBUG，不影响写入。
- 送审时每个文件：本请求之前就有正文、并且整份超过送审预算（`REVIEW_PAYLOAD_MAX_CHARS = 9000`）时，用公共前缀 / 后缀找出改动段，前后各带至多 600 字符原文（按整行对齐），并写明「它前面的 X 字、后面的 Y 字本请求没有改动，没有附上，核对前文事实时再读取」。新建文件、短文件、找不到写入前正文时照旧给整份。之后仍由 `_format_review_payload` 统一截头尾。

**3. 送审内容带系统算好的编辑器字数**

- 每个文件块以「[《标题》编辑器字数 N]」开头（`count_words`，与编辑器、工具的 `word_count` 同一口径）；多个文件时最前面加一行「[本请求写过的正文（编辑器字数）：《A》N、《B》M]」，截头尾时也保得住。
- QUALITY_REVIEWER_PROMPT：报字数改为「[待审查内容] 里系统标出的编辑器字数，或工具结果里的 `word_count` / `new_word_count`」，标出了就不为了字数再读文件；「[质量检查任务]」收尾第一行写「文件名、编辑器字数」。
- 每个角色都遵守的 `AUTHOR_REPLY_PROTOCOL`（base.py，同样进审稿人的系统提示）原来写「按工具返回的 `word_count` 报的字数……工具没给字数就不报字数」，和上一条冲突：自动送审时审稿人这次运行里没有任何工具结果带 `word_count`。改为「按编辑器口径报的字数（工具返回的 `word_count`，或交接内容里系统标出的「编辑器字数」）……两者都没有就不报字数，不估算」，两条规则说同一件事；有测试断言两处都认「编辑器字数」。
- query_files 的 `response_mode` 描述写明：summary 截断时不带 `word_count`，要长文件字数按 id 读 full。这只是把 10-09 的既有行为写进工具说明，免得模型先发一次 summary 再发现没有字数。
- 与 10-09 字数笔记的关系：那条笔记否决了「summary 截断时也给 word_count」（按预览外推是估算；SQL 里按 count_words 的定义算要分 PostgreSQL / SQLite 两套正则），并认为「需要准确字数时按 id 读一次 full 即可」。这里没有改 query_files，仍不外推；改的是审稿人拿字数的来源——系统按落库正文精确计算后直接给它，不再要求为一个数字整份重读（U074 那个文件 14.8 万字符）。

**4. 被「作者手改保护」拒绝的文件写进交接的读写记录**

- `ToolContext.author_edit_refused_file_ids()` 读本请求的 `AuthorEditRefusals`；交接给任何 agent 时，`[本请求的读写记录]` 后追加「[本请求没有改成的文件]: 对《标题》(id=…) 的修改被作者手改保护拒绝了（作者手动改过它们），文件没有改成；不要因为它们没改成就要求返工，需要改时在给作者的回复里问作者；作者在本请求的消息里明确同意改的，以作者的话为准」。标题来自读写守卫（新增公开的 `RepeatReadGuard.file_label`），不知道标题时只有 id。
- 只列拒绝后本请求里始终没写成的文件：减去读写守卫的 `written_file_ids()`。守卫按每一次修改和作者的消息（含中途 steering）判断——同一文件 replace 被拒后改用追加可以写成，作者中途说「可以改大纲」后也会放行——所以既不能把已经写成的文件列成「没改成」，也不能承诺「本请求里工具不会修改它们」，否则又是一条和读写记录、和作者原话冲突的输入。`AuthorEditRefusals` 本身不改：它随 routing 落库给下一轮放行，记的是「问过作者」而不是「最终没写成」。

## Alternatives considered

- **流式检测重复短句 / 思考字数上限 / 降 reasoning_effort / 自动重试**：能缩短作者等待，但都是保护措施，不是触发条件的修复；用户明确要求先修根因，前两轮笔记也已否决。本轮没有引入。
- **在路由层把「补人设」判成 `write_content=false`**（案例 1 的直接前提）：最强理由是从源头消掉错误事实，planner 也不会收到那句约束。没做：路由继承属于 p4 包；而且即使路由判对，这句写给规划师的约束本来就不该进 writer / 审稿人的提示，两处都要修。
- **规划师已交付时不跑计划交接**（I07 建议 2）：最强理由是 U070 那次 writer 根本不需要运行，可以省下一整轮。没做：完成判定归 p1；本包去掉的是 writer 被拉起后收到的那条错误事实。
- **把 `[待审查内容]` 换成整份文件的尾部**：最强理由是实现最简单，追加续写时正好是新内容。被否：返修常常改在文件中间，尾部未必是改动的地方；用写入前正文求改动段对追加、替换、插入都成立。
- **用版本历史还原本请求开始时的正文**：最强理由是不用在写入路径上多记一份内容。被否：要区分本请求内的 AI 版本、「Before AI edit」备份和作者版本，还要重放 diff 链，判断条件多、容易错；写入前正文本来就在写入函数手里，按请求记一份最直接，内存开销是被改文件的一份副本。
- **让 query_files summary 截断时也返回精确 word_count**：最强理由是 writer 自查篇幅时也能省一次全文读取。没做：需要在 SQL 里按 count_words 的定义计数（两种方言），并重做 summary 投影的预算测试；10-09 笔记已权衡过，本轮先只解决审稿人这条路径（证据最集中）。
- **审稿人在「writer 只写完一批、范围还没完」时交接 writer 续写**（案例 2 的第 4 处冲突）：最强理由是作者要的是一次补完。没做：这是「本请求何时算完成」的判定（p1）以及自动送审与分批写作的关系（p2），需要在那里统一决定；本包只把它记成建议。

## Consequences

- writer、审稿人不再收到「作者已经要求写正文、规划完交接 writer」这条写给规划师的约束；规划师照旧收到。案例 1 那种「系统说作者要正文、作者原话只是补设定、又要求已交付就结束」的三方矛盾不再出现在 writer 输入里。
- 长单文件里续写或局部修改后，审稿人拿到的是改动段和前后少量原文，并被告知其余部分没附上；需要核对前文事实时仍要自己读（对 14 万字的文件，这仍然是一次很大的读取，属于正常工作量）。
- 审稿人不必为了报字数而读文件；writer 自己核对篇幅仍按 WRITER_PROMPT 用 query_files(id) 读一次。
- 交接后的 agent 知道哪些文件被作者手改保护拒绝过，不会再把它们列为必改项。
- 写入路径多一次内存记录（每个被改文件在本请求里一份写入前正文的副本），请求结束随 ToolContext 释放。
- **没有修好、也没有宣称修好的部分**：
  - 案例 2 的四处冲突去掉了三处（1、2、3），第 4 处（分批写作被自动送审截断、审稿人无路可走）留给 p1 / p2；四处里哪一处触发了 209k 字思考无法从现有记录确认。
  - 案例 3 的数值核算退化没有找到矛盾指令；案例 4 的 78k 字思考也没有找到确定的触发点。
  - 退化本身是模型在长推理中的输出行为，去掉触发条件不能保证不再出现。
- **再次出现时需要的数据**：该 agent 那一次模型调用的完整思考文本（目前对话记录只留头尾）、完整的模型输入（系统提示 + 交接消息，至少 `[待审查内容]` 与「本轮用户范围约束」两段）、每次模型响应的 usage 与工具调用序列。有了完整思考，才能判断退化开始前在权衡什么。
- **建议（不在本包范围，供集成时处理）**：
  - p4（路由继承）：上一轮已交付、以选项收尾时，作者补设定不应按「A 补问」沿用上一轮的 `write_content=true`（案例 1）；作者对「继续」的回复被路由回没有写权限的审稿人（案例 2 的 05:43）。
  - p1（完成判定）：规划师已交付作者要的全部内容（且没有可写的正文范围）时，不再按计划交接拉起 writer（案例 1）；分批写作时 writer 送审后整轮就结束，作者要的范围永远完不成，需要决定是继续下一批还是收尾并告诉作者已写到哪（案例 2）。
  - p2（自动审稿闸门）：分批写作的中间批次是否送审，与上一条一起定。
  - 作者手改保护：作者用选项编号或「按新来历修改」这类话回答上一轮针对某个文件的提议时，目前不算点名该文件（案例 4 的拒绝本身）。

## Verification
