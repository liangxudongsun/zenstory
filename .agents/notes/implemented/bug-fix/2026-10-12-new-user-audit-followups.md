# Agent Note: 消息发送时间、重载后对话贴底和几处小修（PR175 生产新用户审计跟进）

## Problem

2026-10-12 生产新用户审计（`~/audit-runs/20261012-162011-pr175-new-user-audit/`，评估见同目录 fix-triage.md）里，除编辑版式（见 2026-10-11 edit-file note 的补充）外，还有几处低成本的真实缺陷。手改保护拒绝作者明确授权的问题不在本批：按字符串识别授权的补丁被否决，改为另行设计（见 fix-triage.md）。本批的缺陷：

- 用户消息刷新后显示的是 AI 结束的时间（17:13 发、显示 17:15）：user 行在回合结束时才落库，`created_at` 取落库时刻。
- 刷新 / 重新登录后，对话面板停在倒数第二轮，看不到最后一条回复。本地用 6 轮真实回复复现：桌面差 2938px、手机差 3114px，刷新与 SPA 内重登都一样。历史的 Markdown 懒加载渲染，在第一次贴底之后才把列表撑高，之后没有再贴底。
- 项目「素材」文件夹只收 .txt，同一棵树的「导入正文」收 .txt / .md。
- 浅色主题没有定义 `--foreground-subtle`，版本历史的「编辑」标签、`.btn-secondary`、`.btn-ghost:hover` 在默认的浅色主题下是 #ccc 灰字。
- 长内容等待提示固定写「通常要一两分钟」，高质量多步回合普遍 2.5–7 分钟。

## Decision

- **发送时间**：`process_stream` 在回合开始记 `user_sent_at`，整轮保存（`save_messages`）、停止 / 断线的补偿保存（`_save_partial_history_sync` → `_save_messages_with_session`）、没有产出只留用户消息（`_append_user_messages_sync` 的首条）都用它作 user 行的 `created_at`。回合中消费的 steering 和助手行不变；整轮保存之后才到的 steering 单独追加，不传这个时间，按时间排序仍在助手回复之后。重试去重在本轮写入前执行，不受影响。
- **重载后贴底**：历史加载完后 5 秒内，作者没在列表上滚轮、触摸、点按或按键时，内容变高（`ResizeObserver` 观察列表内容）就继续贴底；作者一动列表就停。流式生成时的贴底逻辑不变。没有 `ResizeObserver` 的环境（jsdom）跳过。
- **素材上传收 .md**：前后端都按纯文本收，和导入正文一致；不解析 Markdown。
- **浅色变量**：`:root.light` 补 `--foreground-subtle: 210 15% 30%`（#414d58）。直接用浅色 `--text-secondary` 时，版本标签在 8% 叠底上只有约 2.9:1，改成这个值后实测 6.1:1。
- **等待提示**：去掉具体时长，改成「写长内容可能要几分钟，请稍等。」，不分档、不按模式切换。

## Alternatives considered

- 用户消息在回合开始时先落库：时间自然准确，但要改历史保存的整体结构（取消 / 失败 / 重试去重都依赖「回合结束时一次写入」），风险远大于收益。
- 贴底只靠 `shouldAutoScrollRef` 门控、不设时间窗：最简单，但作者在底部展开一条历史的思考过程时也会被拉到底，看不到刚展开的内容。
- 服务端记录上次打开的文件，解决换设备回来时编辑区为空：审计里这一点是自动化浏览器清空本地存储造成的，真实用户同设备能恢复，不做。
- 等待提示按已等时长分档：步骤卡片已经显示进度，只要不再承诺具体时长即可。

## Consequences

- 刷新前后用户消息时间一致；按日统计会把跨午夜回合的用户消息算在开始那天，影响可忽略。
- 历史加载后的 5 秒内，作者如果完全不碰列表，晚到的内容（例如图片、懒加载块）仍会把列表拉到底；这正是想要的。作者一滚动就停。
- 超过 2 万字的 .md 按章节规则切分时，有序列表行可能被当成章节标题切碎；.txt 本来也会这样。
- 验证：后端 `tests/test_agent/test_user_message_sent_at.py`（整轮、停止、无产出、晚到 steering 四条；改动前 3 条失败），前端 `ChatPanel.mount.test.tsx` 的贴底用例（改动前失败），`api.test.ts` 与 `test_files.py` 的 .md 用例；本地真实浏览器复现与修复后的桌面 / 手机差距见 PR。
