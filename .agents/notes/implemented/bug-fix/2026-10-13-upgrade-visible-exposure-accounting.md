# 区分升级入口展示，按连续可见范围记录曝光

## Problem

#184：静态额度徽章、常驻卡片被记成 toast，组件内 ref 无法跨同步重挂载去重；后台也无法区分展示次数与独立用户。既有 [保存成功后版本上限仅提醒一次](2026-10-13-file-version-quota-prompt-once.md) 已解决正文重复保存打断，本批补其余统计与 AI 拒绝提示边界。

## Decision

前后端接收 `badge`、`card`，保留 `modal`、历史 `toast`、`page` 原值，不推测改写历史分类。徽章、卡片、升级弹窗复用可见性 hook：按账号、来源/阶段、展示面、位置、额度周期隔离；浏览器通过 IntersectionObserver 与页面可见性判定，持续可见时的 StrictMode、轮询与同步重挂载只记一次。卸载一个提交周期后即结束当前可见范围，真实关闭/离开后重现继续记，不做整会话曝光去重。

主动提醒使用单独的既有 sessionStorage 领取机制。AI 服务端拒绝引发的主动弹窗按账号、限制类型、北京时间额度周期领取一次；输入框的明确受限发送、点击升级、主动历史恢复仍每次反馈。普通保存沿用现有成功语义和版本提醒策略；Pro 不进入免费升级曝光。

聚合保留旧 totals/source 字段，同时按来源和展示面提供曝光次数、曝光独立用户、实际点击次数、点击独立用户、页面到达数。管理页单列这些口径，历史 toast 明示为旧分类。支付结果继续来自既有后端订单/归因区，不把到达当支付，也不以曝光变少推断转化改善。

## Alternatives considered

- 全会话所有曝光只记一次：去重简单，但会掩盖真实关闭再开、来源和阶段变化；只在连续可见范围去重。
- 组件内 ref：成本最低，但同步重挂载会重复；共享内存可见范围，卸载后及时释放。
- 把历史 toast 直接重命名：报表看似统一，但不能证明历史究竟是弹出还是静态；保留原值并明确区分。

## Consequences

新增展示分类的客户端早于 API 发布时，旧 API 会拒绝新分类；丢弃该无效事件，产品行为不受影响，发布后才有完整新口径。不同表中的独立用户不可直接相加。只使用既有事件和元数据，不记录稿件或提示词，不新增付费墙、依赖或迁移。
