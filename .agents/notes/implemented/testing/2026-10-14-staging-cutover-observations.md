# 持卷 API 切流按实际请求验收

## Problem

#214 的发布窗口发生过成簇 502，而静态 health 和发布后 readiness 不能代表真实账号、文件或进行中 SSE 连续可用。现有只读 smoke 面向生产公共接口，既不携带合成账号，也不覆盖切流期间的文件内容。#188 仍有独立的生产套餐数据验收，不能因 staging 或代码合并而关闭。

相关决定：[私有上传对象存储](../architecture/2026-10-07-private-upload-object-storage.md)。对象存储桥保留本地旧引用读取；只启用 S3 不代表卷已无消费者。

## Decision

增加人工运行的 staging-only GET 采样脚本，固定 staging API origin，stdin 接合成账号 token、归属 ID 和稳定文件已知哈希。每周期仅请求当前用户、项目、文件树和文件；验证身份、归属及 UTF-8 正文哈希，只记录状态、时间、request ID 和哈希，不保存正文或 token。失败样本保留，不刷新账号、不重发生成或写入。

脚本只提供读取证据，明确不确认切流、SSE 和 provider source binding。发布文档把实际来源、旧实例排空/退出、新实例 ready、已保存稿件、流终态和额度/账本列为独立验证。已有 volume、300/295 秒预算和中断合同保持不变；本次没有云配置改动或新部署生产者。

## Alternatives considered

- **扩展生产 online-smoke 并携带登录态。** 可复用当前入口，但会扩大生产探测权限，且容易把最终健康与切流验收混同；本次固定 staging 边界。
- **只给 readiness 增加检查。** 有助于发现依赖故障，但无法消除平台持卷不重叠限制，也不能验证用户文件与流结算。
- **先删除卷或增加实例。** 理论上可解除单实例切流约束，但旧上传引用仍需可逆迁移，现有卷也不允许多实例共享；没有相应授权与验证，不能采用。

## Consequences

得到可重复、可关联请求日志的有界证据；保留每次失败，避免用后续成功覆盖。采样并非完整请求覆盖，read probe 也不产生 SSE；实际主流程、mock provider 和云接管仍需独立 staging 验收。#188 的生产备份、迁移与回读继续待授权生产窗口，本次不宣称完成。

## Verification

新增脚本前测试因入口缺失失败；实现后 5 项新增契约及 scripts/ci 全部 47 项通过，覆盖仅 GET、固定 staging origin、身份/文件哈希、401 不刷新、502 保留、网络错误去敏与不输出正文/token。node --check、git diff --check 通过。尚无本次 staging 切流通过声明。

集成前用现有 staging 合成账号只读核对四接口，发现新探针把项目归属误写为 user_id、把文件树误当裸数组；真实 schema 为 owner_id 和 {tree: [...]}。相应 fixture 与错误 owner 反例先红后修，同一内存 token 的实际单轮复跑为四接口 HTTP 200、身份/归属/树中目标与正文哈希全通过。凭据与正文未输出或落入收据；这仅验证探针兼容真实 API，不是部署切流通过证据。
