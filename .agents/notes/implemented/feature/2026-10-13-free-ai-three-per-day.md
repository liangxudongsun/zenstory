# 免费版每日 AI 消息调整为三条

## Problem

用户明确要求控制免费账号 AI 成本，把每日 AI 消息从 10 条改为 3 条，同时保留当天已用次数、在途请求、失败返还和 Pro/其他套餐权益。此项替代 AGENTS 中旧的 10 条规则；历史[额度墙](../feature/2026-10-09-quota-wall-chat-card-and-home-intercept.md)和[停止/返还](../architecture/2026-10-09-agent-graceful-stop-and-no-output-refund.md)的交互与计费机制继续适用。

## Decision

- 免费方案唯一默认值为 3；实际限制、目录接口、新账号与 seed 使用同一默认值。自定义非免费方案缺失 daily key 时保留既有 10 条 fallback，显式配置照读，Pro 仍为 -1。免费项目数 3 和其余权益不变，不新增周额度。
- 数据迁移 20261013_120000 只锁定并更新免费 plan 的 ai_conversations_per_day 与 updated_at，保留其他 JSON 字段。不写 usage_quota，不重置 period、used 或任何已获准预扣。已是 3 时不重复更新时间；回滚仅当值仍为 3 才恢复旧 canonical 10，保留运营之后的修改。
- QuotaService 的账号原子预扣、北京时间日边界、所属日期返还和流式取消/结算源码不改。只剩一条时，并发预扣只有一个成功；旧日期返还不会减少新日次数。已经运行的第三次请求继续完成，另项目的新请求被现有额度墙拦截。
- 首页、公开定价、订阅、用户文档、前端 fallback 与中英测试数据同步每日 3 条。剩余值继续 Math.max(0, limit-used)，历史已用 10 条仍显示真实 used 和 0 剩余；现有恢复时间与 Pro 入口沿用。额度升级按钮手机补足 44px。内部成本保护继续使用现有机制与统一耗尽提示，不展示内部金额/比例。

## Alternatives considered

- 新加周额度能控制长周期成本，但用户明确排除，并会扩大计数与恢复规则；本次只改每日上限。
- 迁移时清空当天计数可以让旧用户都重新领到三条，但会增加当日成本、违反保留用量要求；只更新 plan。
- 为三条重新实现预扣或返还可定制新规则，但既有机制已实现账号共享、原子更新和 charge-period 返还；保留源码，用回归验证边界。
- 直接改所有缺省套餐为三条最少代码，但会悄改自定义套餐的旧权益；保留非免费方案原有 fallback。

## Consequences

免费新请求的每日上限降低，当日已经使用至少三条的账号不能再消耗免费额度；现有在途请求继续，失败是否退还仍按既有产出与错误规则判定。发布需要独立计划数据迁移、真实 staging PostgreSQL 与 API 验收，以及 exact-source CI/E2E 和生产 source/health 回读。上线后成本以实际模型账本测量，额度下降本身不是已经节省成本的证据。

## Verification

新增服务、迁移和 HTTP 回归先失败后通过，包含 legacy plan、used 0/2/3/7、最后一槽并发、跨项目、在途完成、跨日返还与其他方案。后端 210 项扩检通过；PostgreSQL 专用 pytest 需要独立 disposable DB，不对 Railway 现有数据库执行 drop_all。前端新增中英报价、10/3 历史用量与输入保留、额度墙时间、四宽触控检查通过。生产变更前只读基线确认免费 plan 为 10/项目 3，Pro 为 -1/项目 -1；真实环境与最终发布 receipts 保存于私有临时目录，完成后补充结论。
